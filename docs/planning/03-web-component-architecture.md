## 1. Purpose and constraints

The component renders a browser compatibility table from the data in Document 1. Purpose: let an author embed a table that stays correct as support changes, without manually maintaining it.

Three constraints follow and shape every decision below.

**Unopinionated about style, by design.** The component makes no aesthetic decisions on the author's behalf — no opinion on color, typography, or visual identity beyond what the underlying semantics require. What it provides is a clean, semantic, accessible table structure, plus just enough base CSS to make that structure usable without requiring the author to write any styling at all. That base styling stays deliberately minimal and neutral by default, and where color is used to convey meaning — a support state, for instance — it never carries that meaning alone; it is paired with shape or iconography, detailed in §5. Full control over how the table actually looks belongs to the author. This is the primary argument for light DOM (§3).

**Accessible by design, not by remediation.** The multi-dimensional nature of the data (§5) makes this the section with the most engineering risk and the most room for improvement over existing implementations of this kind of table.

**Cheap.** A single documentation page may embed several tables. The component must not require a framework runtime or block on a network round trip to render. Concrete budget in §6.

One further decision belongs here because everything downstream assumes it. **Browser support floor: Baseline 2025.** A compatibility tool that never declares its own compatibility would be an ironic omission, so it is declared: the component targets browsers with Baseline 2025 support or newer — the audience is overwhelmingly developers on current browsers — which comfortably covers the platform features this design leans on (container queries, `@property`, `light-dark()`; all Baseline 2023–2024). Anything newer than the floor is progressive enhancement over a cross-browser default (§5 tracks one such candidate). The floor is documented and versioned with the component; raising it is a deliberate, announced decision, not drift.

## 2. Dependency: Lit

Lit is used. Cost/benefit:

**Gained:** declarative templating with targeted updates, a properties/attributes reflection model that is error-prone to hand-roll, a tested async task primitive for the fetch lifecycle.

**Paid:** roughly 5 KB compressed, plus a reactivity runtime the table does not strictly require given how little post-load state it has (the disclosure interaction is the only state change after data arrives).

A hand-rolled element is feasible given the low dynamism, but correct attribute reflection, batched updates, and lifecycle handling are non-trivial to implement reliably, and the resulting custom implementation would need the same testing investment as Lit already has. Lit is the more efficient choice.

**Constraint:** Lit is an implementation detail, not part of the public contract. No Lit type appears in any exposed attribute, property, event, or CSS surface. Replacing Lit later should require no consumer-facing change.

**Rules the light-DOM render root imposes on the Lit code.** The Lit spike (#187) confirmed that overriding `createRenderRoot()` to append a `<div>` and return it keeps Lit's output inside that container and leaves the author's children untouched, in Chromium, Firefox, and WebKit ([Document 10, #187 section 1](10-component-spikes.md#1-createrenderroot-returning-an-appended-div)). Three rules follow for Phase 2:

- The render container is created in `createRenderRoot()`, never in `connectedCallback()`. Lit calls `createRenderRoot()` only when no render root exists yet, so removing the element and adding it again reuses the one container; creating it in `connectedCallback()` would add a new container on every reconnection ([#187 section 8](10-component-spikes.md#8-removing-the-element-and-adding-it-again)).
- The component does not use `static styles`. Lit adopts `static styles` inside `ReactiveElement.createRenderRoot()`, and the override does not call `super`, so the styles would never apply. This was read from the installed source, not run ([#187, "`static styles`"](10-component-spikes.md#static-styles-source-read-only)). Base styles stay an ordinary stylesheet, as §3 already plans.
- Every reactive property is declared in `static properties`, typed with a `declare` field, and given its default in the constructor. A plain class field (`label = "default"`) shadowed Lit's accessor under TypeScript 7.0.2 and Vite 8.3.8: the development build threw on the first update, and the production build rendered the default once and then ignored every change without an error ([#187 section 4](10-component-spikes.md#4-declare-properties-in-static-properties-under-typescript-7-and-vite-8)).

The same budget discipline governs `@bcd-embed/schema`: the element imports its types only (`import type`), never Zod at runtime. Zod is roughly twice Lit's size, and its runtime validation earns its keep on the server and at build time, not in the browser (Document 2 §2) — a malformed payload here is an error state (§4, "Fallback content"), not a schema-validation report.

## 3. Light DOM default

The component renders into light DOM by default — not as a fallback, but as the primary design.

Rationale specific to this component: the table is the author's content and should inherit the author's existing table styles, typography scale, color tokens, and print stylesheet without reintroduction through custom properties. A shadow root would sever all of that and require rebuilding it property-by-property.

**Decided: no shadow DOM anywhere in this component.** The disclosure (§5) is built on native `<details>`/`<summary>` rather than a custom widget, and native elements carry their own semantics without needing encapsulation to protect them — there is nothing left that would justify a shadow root. This resolves what was previously an open question in favor of the simpler answer: light DOM throughout, full stop.

**Declarative Shadow DOM (DSD) is not needed.** DSD exists to let a server or build step emit shadow content as HTML that hydrates without a flash — but with no shadow root anywhere in this component, there is no shadow content to declare, in any mode, current or deferred. If full server-side rendering of the markup is ever built (§7 — currently deferred, not v1), it would be plain server-rendered light-DOM HTML, including the native `<details>`/`<summary>` disclosure, functional before any hydration attaches; no DSD-equivalent mechanism would be required.

### Cascade layers

Light DOM means base styles have no encapsulation and can collide with author styles. Mitigation: cascade layers — declared explicitly, with the actual CSS imported into the declared layer rather than wrapped inline in one large block.

```css
/* packages/element/src/styles/base.css, as #200 built it */
@layer bcd-embed.base;

@import url("./properties.css"); /* the @property rules, deliberately not in a layer */
@import url("./tokens.css") layer(bcd-embed.base); /* the palette, applied to each icon */
@import url("./table.css") layer(bcd-embed.base); /* structure, focus, the fallback rule, the sticky column */
```

#201 was to add `container-queries.css`, but it ships no container query, so there is no such file: the sticky feature column sits in `table.css` (§5, "Responsive behavior", says why). Print needs no file of its own either: the rules that only make sense on a screen, the region's `overflow` and the sticky column, sit inside `@media not print`, so print gets the table in the flow without a rule that undoes them.

**`@property` rules are imported without `layer()`.** When the tooling spike (#188) flattened `@import ... layer()` into one file, every tool it tried (Vite's own CSS pipeline, `lightningcss` 1.33.0, and `postcss-import` 17.0.1) nested an `@property` rule inside its `@layer` block. Chromium, Firefox, and WebKit still register an `@property` rule inside `@layer` in a document stylesheet, but importing the file that holds the `@property` rules without `layer()` keeps them at the top level, which `lightningcss` and `postcss-import` both confirmed ([Document 10, #188 section 6](10-component-spikes.md#6-flattening-import--layer-into-one-basecss)). The spike did not check Vite's own pipeline with this unlayered import. #200 did, on the built `dist/base.css`: Vite 8.3.8 kept every `@property` rule at the top level and wrapped each layered import in its own `@layer bcd-embed.base { }` block, and a test in `packages/element/tests/package.test.ts` checks that shape on every build.

**The published `base.css` is flattened with Vite's CSS pipeline and `build.cssMinify: false`.** In Vite 8.3.8 the default of `build.cssMinify` is `'lightningcss'` (`vite/dist/node/index.d.ts`, line 2798). The spike did not build with that default; it ran lightningcss directly and as Vite's CSS transformer, and in both runs lightningcss dropped the `@layer` order statement and rewrote values, so the default minifier would likely do the same. With `cssMinify: false`, Vite kept the order statement and left values unchanged ([#188 section 6](10-component-spikes.md#6-flattening-import--layer-into-one-basecss)). If a minified file is wanted, it is a separate, measured step. #200 builds the stylesheet as a second library entry, which needs `build.cssCodeSplit: true`: library mode turns code splitting off, and Vite 8.3.8 then refuses a CSS file among the inputs. The built file measures 2.94 kB with Brotli, comments included, against a `size-limit` budget of 3 kB.

**`@property` does not register inside a shadow root today.** Chromium 159, Firefox 159, and WebKit 27.2 all ignored an `@property` rule in a shadow root's `<style>` element, inside `@layer` there, and in an adopted stylesheet, although the CSS Properties and Values API editor's draft (section 2.8) says registrations are not scoped to a tree scope ([#188 section 6](10-component-spikes.md#6-flattening-import--layer-into-one-basecss)). The component has no shadow root, so its own `base.css` is unaffected when the page loads it. It does matter to an author who places `<bcd-compat-table>` inside their own shadow root and loads `base.css` there: the custom properties then stay unregistered. The author documentation must say to load `base.css` from the document. Re-run the spike's `property-probe.mjs` when Playwright's browsers are upgraded, because this changes when the engines implement the draft.

Declaring the layer name up front, separately from importing content into it, is deliberate rather than a stylistic preference: it fixes this layer's position in the cascade order the moment the stylesheet is parsed, before any of the actual rules are known, and it lets the base styles live as ordinary, layer-agnostic CSS files in the source tree — each `@import ... layer(...)` is what assigns a file to the layer, not a wrapping block inside it. This also scales cleanly if the base styles end up split across more than one concern (table structure, design tokens, container-query breakpoints) without needing repeated `@layer bcd-embed.base { }` wrappers in every file.

Any un-layered author style overrides layered styles regardless of specificity, so authors override the component with ordinary CSS and no `!important`. Authors using layers themselves can order this layer explicitly relative to their own, since its name is declared and stable.

Base styles are shipped as a separate, opt-in stylesheet. A consumer wanting only semantic markup imports nothing. That promise has one exception, accepted by the owner on 20 November 2026: without the stylesheet, the author's fallback content stays visible next to the loaded table, because the base stylesheet is what hides it (§4, "Fallback content").

Two standing rules govern every line of CSS this project authors and ships, not just the base stylesheet: every custom property is registered via `@property` unless there is a specific, stated reason not to — the token surface in §4 is where this is worked through in detail — and every property and value is logical, not physical: `inline-size`/`block-size` rather than `width`/`height`, `margin-inline`/`margin-block` rather than `margin-left`/`margin-right`/`margin-top`/`margin-bottom`, `inset-inline-start` rather than `left`, and so on throughout. This is what makes the component's layout correct under RTL and vertical writing modes without separate handling, and it costs nothing extra to do from the start.

## 4. Public API

### Element

```html
<bcd-compat-table query="css.properties.display"></bcd-compat-table>
```

**Attributes/properties.**
- `query` — BCD dotted key. Only required input.
- `endpoint` — overrides the API base URL. This is the entire self-hosting mechanism. The default is `https://api.browser-compat.dev`, the hosted API's hostname (Document 9). The element requests `{endpoint}/v1/current/features/{query}.json`, the feature lookup route in Document 1 §4.1, and a trailing slash on `endpoint` does not produce a double slash. For the default, `query="css.properties.display"` requests exactly `https://api.browser-compat.dev/v1/current/features/css.properties.display.json` (#202). The value must be an absolute `https:` or `http:` URL with no credentials, query string, or fragment; any other value, such as an empty string or one containing `?`, is the error `invalid-endpoint`, and no request is sent (#203). `http:` is accepted for any host, for a self-hosted API, typically on a local machine; a browser blocks an `http:` request from an `https:` page as mixed content, which the element reports as `network`.
- `browsers` — optional space-separated override of the displayed support-target set (browsers and runtimes, Document 1 §5.1). The default is `chrome firefox safari nodejs` — the three independent rendering engines plus Node.js, not a popularity pick (§11) — **intersected with the support targets actually present in the payload**: Node.js appears on a `javascript.builtins.*` table and not on a `css.*` one, where a permanently empty column would be noise. An explicitly set `browsers` attribute is honored literally — a listed target absent from the payload renders as a "no data" column, because the author asked for it (§11). The API itself returns everything; this attribute is the only curation point.
- `locale` — selects the string table ("Strings and localization readiness," below). v1 ships English only; the attribute exists from the start so adding a locale later is additive, not breaking.
- `loading` — `lazy` (default) or `eager`. Mirrors native `<img loading>` rather than inventing new vocabulary. `lazy` is the `IntersectionObserver`-deferred behavior in §6, the right default given several tables per page is the stated design case; `eager` opts a specific instance out — a table already known to be above the fold, or test automation where waiting on intersection timing adds flakiness rather than value. As for `<img loading>`, the value is read case-insensitively, and a missing or unknown value means the default, `lazy` (#203). The observer uses a `rootMargin` of 400 pixels, so the request starts shortly before the element scrolls into view; in a cross-origin iframe the browser ignores the margin, and the request starts when the element enters the viewport. `lazy` holds back only the first request: once the element has come near the viewport or sent a request, a later `query` requests at once, and switching to `lazy` does not unload a table. A `query` that fails the key pattern, or an `endpoint` that is not a base URL, sends no request, so nothing is held back for it: the error fires at once and no observer is attached. Two limits follow from the observer (#203). It reports only on an element that has a box, so a host styled `display: none` or `display: contents` never sends its request and fires no event; such a host needs `loading="eager"`. And the margin applies to the viewport, not to a scrolling ancestor, so inside an `overflow: auto` box the request starts only when the element is visible within that box.
- `.data` (property only) — a contract-conformant payload set directly. When present, no fetch occurs, so `loading` has no effect: there is nothing to defer. This is the build-time property-assignment path (§7).
- `source` — the `id` of a `<script type="application/json">` element carrying a contract-conformant payload. Read once for each id, no fetch, no script execution required beyond the component's own (§7). The first read happens in `connectedCallback`, and the script's text is parsed once: changing it afterwards changes nothing. When the script comes after the element, the element waits for the parser to reach it (§7 gives the reason and the rule). An `id` that matches no element, or whose first match in tree order is not a `<script type="application/json">`, is the error `source-missing`; text that is not JSON, or is empty, is `source-invalid-json`; JSON that fails the payload guard is `invalid-payload` (#205). If `query`, `.data`, and `source` are somehow set simultaneously, the documented total order is `.data`, then `source`, then `query`: an already-present payload is never discarded in favor of a network request, and between the two payload paths the directly assigned property wins — it is the more explicit act, and the only one that can be updated programmatically at runtime. A failed `source` does not fall through to `query`: the element reports the error and sends no request (#205). The same holds while `source` is waiting for the parser: a present `source` keeps the element out of fetch mode until the attribute is removed. While `data` is set the element does not read `source` at all, and setting `data` while it waits for the parser cancels the wait, so the script is not parsed for nothing and a broken reference reports nothing; clearing `data` reads it then, once, and a later `data` assignment and clearing shows the held read again without parsing again (#205).

**Multiple features.** Use multiple elements rather than a `query` list attribute. Each element needs independent loading state, error state, and cache entry, and stacking several features into one table is an authoring decision, not a component default. BCD's own key nesting (a query returning a parent and its descendants) is already one table by definition and is handled without special-casing.

**Placement.** The element cannot be written directly inside `<table>`, `<tbody>`, `<thead>`, `<tfoot>`, or `<tr>` in HTML. The HTML parser moves it out, to just before the table, with its children; this happened in Chromium, Firefox, and WebKit with no script on the page. Inside a `<td>` it stays where it was written ([Document 10, #187 section 7](10-component-spikes.md#7-bcd-compat-table-written-directly-inside-a-table)). The spike tested a direct child of `<table>` only; the other four follow from the HTML Standard's "in table body" and "in row" insertion modes, which hand an unexpected start tag to the "in table" mode and its foster parenting. These parsing rules also apply to `innerHTML`, but not to a script that inserts the element with `appendChild`. The author documentation states this rule.

### Events

The element dispatches two events, named by the owner on 18 November 2026: `bcd-load` and `bcd-error`. The `bcd-` prefix keeps them from colliding with the native `load` and `error` events. Each is a `CustomEvent` dispatched on the element with a plain-object `detail`. Both events bubble (`bubbles: true`) and keep every other event option at its default, so neither can be cancelled. #198 built them this way because it was the plan's default, and the owner accepted it on 20 November 2026. Because they bubble, one listener on the document hears every table on the page. A host page uses `bcd-error` to detect a failed table rather than let it fail silently.

```ts
type BcdMode = "data" | "source" | "fetch"; // which input supplied the payload (or failed)

type BcdLoadDetail = {
  mode: BcdMode;
  snapshot: string | null; // fetch mode: the response's `bcd-embed-snapshot` header (Document 1 §7); otherwise null
};

type BcdErrorReason =
  | "invalid-query" // `query` fails the key pattern; no request is sent
  | "invalid-endpoint" // `endpoint` is not an https: or http: base URL; no request is sent (#203)
  | "network" // the request failed with no readable response, including the edge's 429 (Document 1 §8)
  | "http" // the API answered with an error status
  | "invalid-payload" // the body, the `source` JSON, or the `.data` value is not a contract-conformant payload
  | "source-missing" // `source` names no `<script type="application/json">`
  | "source-invalid-json"; // the `source` script's text is not JSON

type BcdErrorDetail = {
  mode: BcdMode;
  reason: BcdErrorReason;
  status: number | null; // the HTTP status for "http"; null for every other reason
  code: string | null; // the contract's error code, such as "feature_not_found", when the body carries one; otherwise null
};
```

`bcd-load` fires once for each update that renders a newly assigned payload, after the table is in the document. In fetch mode the same holds for each new request: an event fires when its answer renders or fails, and a pending or waiting state fires nothing (#203). `bcd-error` fires once for each update that rejects a newly assigned value, and the element never retries by itself. Three details make "once" precise (#198). The element updates in a batch, so two payloads assigned one after the other in the same task render the second and fire one event. Assigning the object that is already assigned is no change, so nothing renders and nothing fires; a page that changes a payload in place must assign a new object. And an event never fires while the element is out of the document: an update that finishes then holds its event back, and the element dispatches one event, for the state it is in, when it is connected again. That keeps the promise that a listener on the document hears an event for every rendered payload. In source mode (#205) the same rules hold, and a change to the `source` attribute counts as a new input, so it fires one event. A wait for the parser fires nothing, and the event fires when the wait ends. A change to `browsers` or `locale` renders the same payload again and fires nothing, with one exception that #198 found: the table model checks only the support targets it displays, so a `browsers` change can turn a rendered payload into a rejected one, when it asks for a target whose `browsers` entry is malformed. That change fires `bcd-error`, and a change back fires `bcd-load`. The detail values are fixed by the acceptance criteria of the issues that build them: #198 (`mode: "data"`, `snapshot: null`, and `invalid-payload` with `status: null` and `code: null`), #202 (`invalid-query`, `network` with `status: null`, `http` with `status: 404` and `code: "feature_not_found"`, a 404 with no `code` in its body giving `code: null`, and a non-JSON 200 body giving `invalid-payload`), #203 (`mode: "fetch"` with a non-empty `snapshot`, and `invalid-endpoint`), and #205 (`mode: "source"`, `source-missing`, `source-invalid-json`, and `invalid-payload`).

### Fallback content

The author's children are the fallback. The element renders its table into a render container it creates and owns (§2), next to the children, and never moves or removes them, because in the Lit spike React threw a `removeChild` error on its next update and unmounted the whole root when the element had removed children React rendered ([Document 10, #187 section 3](10-component-spikes.md#element-children-removing-them-the-contrast)). A `<slot>` is never used: outside a shadow tree it projects nothing and renders its own fallback text as `display: contents`, so it would show stray text ([#187 section 2](10-component-spikes.md#2-a-slot-in-a-light-dom-template)).

**How the fallback is retired, decided by the owner on 20 November 2026.** The element sets a state attribute on itself, and a rule in the base stylesheet hides every child except the render container while that attribute is present. This amendment names the attribute `loaded`, a boolean attribute that only the element sets: it is present while a table is rendered and removed on an error or when `.data` becomes `null`. The render container carries the class `bcd-render-container`, which is part of the public class names (§4, "Styling surface"). An earlier draft set `hidden` on each element child once, when the table loaded; the Lit spike showed that this snapshot misses a child a framework adds later, which stays visible after the table, and a text-only fallback, because a text node cannot carry `hidden` ([#187 section 3](10-component-spikes.md#element-children-hiding-with-hidden), [#187 findings 3 and 4](10-component-spikes.md#findings-for-the-document-3-amendment-192)). A rule keyed on the host covers both, and also covers children the parser adds after the first render, because it applies to whatever children exist at any moment.

CSS selectors match elements, not text nodes, so the rule needs two parts. The element children are removed with `display: none`, and the text is hidden by making the host invisible and the container visible again. The block below is the rule as #198 tested it; #200 added a third part, described after the measurements, that stops bare text from taking space:

```css
bcd-compat-table[loaded] {
  visibility: hidden; /* hides bare text children; the space they take remains */
}

bcd-compat-table[loaded] > :not(.bcd-render-container) {
  display: none; /* removes element children, including ones added later */
}

bcd-compat-table[loaded] > .bcd-render-container {
  visibility: visible; /* the table shows again */
}
```

`visibility: hidden` also removes the text from the accessibility tree, but a bare text fallback keeps its line box, so a blank line can remain above or below the table. #198 verified this rule in Playwright 1.65.1's Chromium, Firefox, and WebKit (`packages/element/e2e/data-mode.e2e.ts`). In all three, a `<p>` fallback computes to `display: none` while `loaded` is present and to `display: block` again once it is removed, the element computes to `visibility: hidden`, and the render container and the table compute to `visibility: visible`. A one-line bare text fallback left 18 px of blank space in Chromium and WebKit and 19.2 px in Firefox, which is one line at the default font size, and its text was absent from the element's `innerText`. #198's acceptance criterion that the `<p>` fallback gets `hidden` is replaced by these checks of the attribute and the computed styles. #200 moved the rule into the base stylesheet (`packages/element/src/styles/table.css`) and deleted the fixture's copy, so the browser tests now load the built `dist/base.css` and check the rule as authors get it.

**#200 removes the blank line.** Review of #200 reproduced the band left by a bare text fallback: a `<bcd-compat-table>` holding "Loading the table, please wait…" pushed its table 18 px down in Chromium. While `loaded` is present, the element is now a one-column grid (`grid-template-columns: minmax(0, 1fr)`, `grid-auto-rows: 0`), and the render container is placed in the first row (`grid-row: 1; grid-column: 1`). The grid wraps bare text in an anonymous item, which auto-placement puts in a later row of zero height, and `visibility: hidden` still keeps it unseen. Text that is only white space makes no item. The font is left alone, so the table keeps the page's font size and line height, and a token in `em` still follows them; zeroing the host's `font-size` would have needed a way to restore the page's size on the container, which `inherit` cannot give. In Playwright 1.65.1's three engines, the render container now starts at the element's top and the element is no taller than the container, for an element child, bare text, and both together, and both kinds of fallback come back when `loaded` is removed (`packages/element/e2e/base-stylesheet.e2e.ts`). The 18 px and 19.2 px measured above are now 0 px (`packages/element/e2e/data-mode.e2e.ts`).

**Without the stylesheet, the fallback stays visible next to the table.** The owner accepted this on 20 November 2026, because a page that loads the component but not its stylesheet is very rare. It changes Document 3's promise that a page importing nothing still gets usable output (§3): the table is still complete and accessible, but the fallback is no longer hidden.

| State                        | Author's children                                        | The element adds                                                                           |
| ---------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| No script, or before upgrade | Visible                                                  | Nothing                                                                                    |
| Loading (fetch mode)         | Visible                                                  | `aria-busy="true"` on the element while the request is in flight                           |
| Loaded                       | Hidden by the base stylesheet, while `loaded` is present | The table, inside the render container, and the `loaded` attribute; `aria-busy` is removed |
| Error                        | Visible again (`loaded` removed)                         | A `bcd-error` event                                                                        |

When the author gave no children, the element renders a sentence of its own while loading and after an error; the data-mode error came first and the fetch-mode sentences follow below. The scaffold branch for #194 adds the message ids `loading` ("Loading browser compatibility data for {query}.") and `error` ("Browser compatibility data for {query} could not be loaded.") to `packages/element/src/strings/en.ts`. The owner decided the data-mode error on 20 November 2026, and #198 built it. When the author gave fallback content, the element renders nothing of its own, and the fallback is the message, visible again because `loaded` is not set. When the author gave none, the element renders one sentence in its render container, `<p class="bcd-error">Browser compatibility data could not be shown.</p>`, so an element with no children is never empty after an error, for assistive technology too. The sentence is the message `error-no-query`. It names no query because a value that is not a payload may have none, which is why the `error` sentence cannot be used here. Fallback content means an element child other than the render container, or text that is not only white space; a comment and the line breaks between tags do not count. The element checks again whenever its children change, so the sentence goes when a framework or the parser adds a child later. The paragraph is not a live region. #203 settled the two sentences in fetch mode, where the `query` attribute is always known. With no fallback content, a lazy element that is still waiting for the viewport renders `<p class="bcd-loading">Browser compatibility data for {query} has not loaded yet.</p>` (the message `not-loaded`), which claims no load because nothing has been requested and the wait may never end. While the request is in flight it renders `<p class="bcd-loading">Loading browser compatibility data for {query}.</p>`, and `<p class="bcd-error">Browser compatibility data for {query} could not be loaded.</p>` after any fetch-mode error. A fetch error for an empty `query` uses the `error-no-query` sentence, because there is nothing to name. Neither paragraph is a live region, and the element never moves focus. `bcd-loading` joins the public class names.

`aria-busy="true"` is set while a request is in flight and removed when the answer renders or fails (#203). A lazy element that is still waiting for the viewport does not carry it, because that wait may never end. The element removes only the value it set, so an author's own `aria-busy` is neither overwritten nor removed. Restoring the `query` and `endpoint` of the element's latest successful answer, after `query` was removed or `data` was set and cleared, renders that table again in the same update with no pending state and no request, and fires one `bcd-load`, because that update changed the input. A failure is not remembered: restoring after one asks the feature client again, which answers with the held failure inside its 10-second window and sends one request after it. Assigning the value `query` already has is no change and does nothing. Setting `.data` to `null` after a render removes the table and shows the fallback again (#198). No live region announces loading, so a page with ten tables produces no status announcement (#203). What each screen reader says on reaching a loading element is recorded as an expectation in `packages/element/README.md` and is not yet verified; the CI walks cover the loaded table only.

The render container's position among the children is not fixed. It comes after the author's children when the element is upgraded after parsing, and before them when the element is defined before the parser reaches it, because the container is appended on the first connection and the parser then adds the children after it ([#187, "Where the container lands"](10-component-spikes.md#where-the-container-lands-depends-on-when-the-element-is-defined)). Base styles and tests must allow both orders. The rule above does, because it does not depend on order.

**React replacing a string child is not solved by the state attribute.** When React changes a single string child, it assigns the element's `textContent`, which removes every child, the render container included. Lit keeps its reference to the detached container and renders into it, so the table silently stops appearing, with no error ([#187 section 3](10-component-spikes.md#a-single-string-child)). The stylesheet rule cannot help, because the container is no longer in the document. #198 must detect a detached container and put it back, for example with a `MutationObserver` on the element's child list that re-appends the container when it is no longer a child. It must re-append the same container node rather than create a new one, because Lit creates the render root only once and keeps rendering into that node ([#187 section 8](10-component-spikes.md#8-removing-the-element-and-adding-it-again)). #198 built this: a `MutationObserver` on the element's child list appends the same container again when it is no longer a child, and `connectedCallback` does the same for a container removed while the element was out of the document. A browser test in #198 assigns `textContent`, as React does, and finds the table back after one microtask; the framework fixtures (#207) show it under real React 19.3.1 and Vue 3.5.45, where the table is back after the framework's string update (Svelte updates a text node and never touches the container).

**A deep copy of a rendered element drops the copied table.** `cloneNode(true)`, or HTML saved from a rendered page, carries a copy of the render container and its table, caption `id` included, but not the `data` property. The copy would show a second, stale table and duplicate the `id`. So the element removes any child other than its own container that has the class `bcd-render-container`, when it creates its container and whenever its child list changes afterwards, which covers saved HTML that the parser adds after an early-defined element has connected (#198). That child is the element's own earlier output, never author content, so the rule that the element never removes the author's children still holds. The class is reserved for the element: an author's own child that carries it is removed too. The owner accepted this on 20 November 2026. Authors under React can also avoid the case by writing the fallback as an element rather than a bare string (§8).

### Support-target columns

The `browsers` rules above decide which targets show. The table model (#196) groups the shown targets into column groups by their `type` in the payload (`desktop`, `mobile`, `xr`, or `server`, Document 1 §4.2). Three further rules are settled:

- **The "Other" group.** A target named in an explicit `browsers` attribute but absent from the payload has no `type`, so it goes into a group named "Other", and every cell in its column is "No data for {target}". For `browsers="chrome deno"` and a payload with no `deno`, the table has an "Other" group with one column headed `deno` (#196).
- **The empty intersection.** When `browsers` is not set and none of the default targets (`chrome firefox safari nodejs`) is in the payload, the model shows the payload's own targets instead of an empty table. A payload whose only target is `webview_android` shows that one target (#196).
- **The column group order.** The groups appear in the order Desktop, Mobile, Server, XR, Other. The owner decided this on 20 November 2026, because it matches the compatibility tables on MDN Web Docs. A group with no shown target is left out, so the Phase 1 fixture still reads Desktop, then Server (Document 7). The table model (#196) applies this order.

### Strings and localization readiness

v1 is English-only, but internationalization shares a property with accessibility: bolted on later, it means reopening every template. The door is held open structurally from the first line of code:

- Every human-readable string the component renders — including the generated accessible names in §5, which are full sentences, not labels — lives in a single strings module keyed by message id, with placeholders for interpolated values (`supported-since: "Supported since {target} {version}"`, as in Document 7's string inventory). No string literal appears in a template.
- Accessible-name sentences are messages with placeholders, never concatenated fragments — word order differs across languages, and concatenation is the classic mistake that turns later localization into a rewrite instead of a translation.
- The `locale` attribute selects the string table; unknown locales fall back to English. Locale tables beyond English load on demand (dynamic import), so the English-only default pays no bundle cost for a capability it is not using.
- The model to draw from is MDN's own localization pipeline (`mdn/content` with its `mdn/translated-content` counterpart, community-translated via Mozilla's Pontoon): a strings file in the repository first, Pontoon integration later if and when translation contributions are wanted. The strings-file format should be chosen with Pontoon's supported formats in mind — Fluent being the Mozilla-native choice — so that step is an integration, not a migration.

The Phase 1 markup exercise (§10) produces the initial string inventory as a side effect: hand-writing the target markup enumerates every sentence the component will ever generate.

### Styling surface

Theming uses registered custom properties. This is the default for every custom property the component exposes, not just the color example below — registration gives type checking via `syntax`, a guaranteed `initial-value` so nothing silently inherits an unset value, and animatability that an unregistered `--custom-prop` doesn't get. A property is left unregistered only for a specific, stated reason (for instance, a value type `@property`'s `syntax` grammar cannot express), not by default or oversight:

```css
@property --bcd-color-supported {
  syntax: "<color>";
  inherits: true;
  initial-value: canvastext;
}
```

The token surface covers support-state colors, spacing, border treatment, and the icon set. Layout and typography are controlled through the ordinary cascade, since light DOM already exposes them; custom properties are the design-token surface, not the primary styling mechanism. This distinction should be stated in the documentation, since it differs from typical shadow-DOM component conventions.

**The tokens as #200 built them.** `packages/element/README.md` ("Styling") lists every token with its type and default. Three decisions shape the list:

- **Each colour is a pair of tokens, `-light` and `-dark`, and the stylesheet chooses with `light-dark()` where the colour is used.** A single registered token cannot carry both: a registered `<color>` is resolved to one colour where it is computed, and Chromium 159, Firefox 159, and WebKit 27.2 all resolved an `initial-value` of `light-dark(#000, #fff)` to its light colour, even inside an element with `color-scheme: dark`. Choosing at the point of use follows the scheme the table inherits. The example above, with `initial-value: canvastext`, is superseded, because the three engines also resolved `canvastext` to one fixed colour.
- **The defaults live in the `initial-value` of each `@property` rule, and nothing in the layer sets a token.** Every token inherits, so an author can set one on the element, on any ancestor, or on `:root`. A layered declaration on the element would have silently beaten an author's value on `:root`, because a value set on the element always beats an inherited one.
- **Three spacing and size tokens stay unregistered: `--bcd-cell-padding` (`0.5rem`), `--bcd-indent` (`1rem`), and `--bcd-icon-size` (`1em`).** An `initial-value` must be computationally independent, which a length in `rem` or `em` is not, and all three engines rejected one. A pixel default would stop the padding and the icon from following the reader's text size, so the stylesheet reads these three with a `var()` fallback instead. `properties.css` lists each with its reason, and a test fails on any custom property that is neither registered nor listed.

The icon set is part of the markup, not a token (§5), so an author replaces an icon by hiding `.bcd-icon` and drawing their own.

The stylesheet sets no `color-scheme`, no background, and no text colour. The background behind the table is the page's, so the page's scheme decides which palette stays readable on it. A page with `color-scheme: light dark` gets the dark colours when the reader prefers a dark scheme, and a page that declares no scheme gets the light ones. The element that sets a dark scheme must also paint a dark background, such as `background-color: Canvas`: `light-dark()` follows the inherited scheme whether or not anything dark is painted, and on white the dark state colours reach only 2.28:1 to 3.10:1. The adversarial review of #200 found this; the package README states it, and the dark-scheme browser test sets the background.

Rendered class names are part of the public contract once anyone styles against them. They are namespaced, documented, and versioned. The element renders `bcd-render-container`, `bcd-scroller`, `bcd-table`, `bcd-feature`, `bcd-feature-depth-{n}`, `bcd-history`, `bcd-history-list`, and `bcd-error` (#198), `bcd-loading` (#203), and `bcd-icon` with `bcd-icon-{state}` on each icon (#200, §5). One class is not namespaced: `visually-hidden`, on the span that holds a cell's full sentence, as in the Phase 1 markup. The owner accepted it as built on 20 November 2026. A page that already has a `visually-hidden` rule of its own therefore applies it to those spans, which is the effect the base stylesheet's rule has. The base stylesheet scopes its own rule to `.bcd-table .visually-hidden`, so it never reaches an element of the page outside the table.

## 5. Accessibility

The data is multi-dimensional: feature, by support target (browser or runtime), by version, with modifiers for partial support, flags, prefixes, alternative names, removal, and notes. Compressing this into a two-dimensional grid is where accessibility failures typically originate, and the failure cannot be corrected after the fact with added ARIA — the underlying structure has to be right.

### Native semantics

A real `<table>` with `<thead>`, `<tbody>`, `<th>`, `<td>` — not a grid of `div`s with `role="table"`. This also preserves compatibility with print stylesheets, reader modes, and copy-to-spreadsheet.

The header is two-tiered (a platform row above a support-target row — Chrome, Node, Deno, and so on, per Document 1 §5.1), so `scope` alone may be insufficient. `scope="colgroup"` on platform headers and `scope="col"` on support-target headers is the baseline; for a header this dense, explicit `headers`/`id` association may be required to guarantee correct announcement (e.g., "display, Chrome, supported since version 1"). This must be verified against actual assistive technology, not assumed from the specification. A `<caption>` names the table; the feature name is a row header (`<th scope="row">`), not a data cell.

### Per-cell accessible names

Every cell requires a programmatically determinable name stating the complete fact — "Supported since Chrome 29," not a bare checkmark; "No support," not a colored box; "Partial support since Firefox 63, see note," not an icon alone. A cell whose meaning depends solely on icon color fails WCAG 1.4.1 and communicates nothing to a screen reader.

Lucide is a reasonable source for the icon set: MIT-licensed (matches the project's own licensing decision, Document 2 §2), plain SVG at its core rather than tied to a specific framework, so it fits a light-DOM component without needing a React-specific wrapper, and its line-icon style pairs cleanly with the shape-based non-color affordances this section already requires — a check for supported, an x for unsupported, a dash or slash for unknown, and so on. The specific icon-to-state mapping is an implementation detail to settle during Phase 3 (§10), alongside the ColorADD/ColorSym-informed palette (below), not a decision this document needs to fix in advance.

**The icon mapping and the palette, as #200 built them.** The icons are inline SVG, drawn for this project on a 24 by 24 grid as strokes in `currentColor`, one `<path>` each, in `packages/element/src/render/status.ts`. No Lucide path is used, so no licence notice is needed. Inline SVG was chosen over an icon drawn by CSS (a `mask-image` on a pseudo-element) for three reasons, each from a constraint above. In forced colours the browser replaces `color` and the stroke follows it, while a CSS mask is painted with `background-color`, which forced colours replaces with the background colour; the only fix, `forced-color-adjust`, has limited availability. Print often leaves backgrounds out, and a masked icon is a background. And a mask needs a URL, which a page's Content Security Policy can block. The cost is two elements per cell, which raises the bound in `packages/element/src/render/table.ts` from 7 to 9 elements per cell.

A full preview shared the supported glyph in Phase 1. #200 gave it the flask, so every support state in the contract (`supported`, `partial`, `preview`, `unsupported`, `unknown`) and "no data" has its own shape, which a test asserts. The palette follows ColorADD's and ColorSym's premise rather than their symbols: colour is paired with shape, so a reader who cannot tell red from green still has the check and the cross. `unknown` and `no-data` share a grey, because their shapes already differ.

Implementation: the icon is decorative and hidden from assistive technology; visible cell text carries the version; a visually hidden span carries the full accessible name. Modifiers (flag, prefix, alternative name, partial, removed) are part of that name, not separate icons requiring reconstruction by the reader.

**The compact glyph span carries `hidden` as well as `aria-hidden="true"`.** The owner decided this on 18 November 2026, and the Phase 1 pages carry it since #216 (Document 7, "What is here"). With no stylesheet, the browser's own `hidden` rule removes the glyph-and-version span, so each cell reads as its full sentence, and a page that imports nothing (§3) still gets a usable table. The base stylesheet must give the span its `display` back, as the Phase 1 stylesheet does with `.bcd-table [aria-hidden="true"][hidden] { display: inline; }` (`docs/planning/phase1-markup/phase1.css`), or a sighted reader never sees the icon. The attribute selector keeps that rule off every other hidden element. #200's base stylesheet carries the same rule (`packages/element/src/styles/table.css`), and a three-engine test checks that the icon and version show with it and the sentence shows without it.

**"Or earlier" is shown only when the payload says so.** The table model reads `versionAddedIsApproximate` on the support summary as an optional field. It writes "Supported since {target} {version} or earlier", with a compact `≤` before the version, only when the field is present and `true`. When the field is absent, as in every contract 1.0.0 summary, or `false`, the cell reads as an exact version. The model never derives the flag from the branches, because selecting a statement repeats the API's logic in the component, which `CLAUDE.md` rules out (#196). Contract 1.1.0 adds the field to the summary (#191); until then, no summary carries it, because the 1.0.0 summary has `versionRemovedIsApproximate` but not its "added" twin (`packages/schema/src/schemas.ts`, lines 219–225).

**The table model applies these rules (#196).** `packages/element/src/model/table-model.ts` builds the columns, rows, cells, and every sentence from the payload in one pass, with no DOM. Its rules, beyond the ones above:

| Question                              | Rule                                                                                                                                                                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Which sentence names a cell?          | The summary's `state` picks the sentence. A sentence carries at most one modifier, chosen in the order flag, prefix, alternative name. In a preview state, partial support wins over the flag, so the flag is named only in the disclosure. An approximate version inside a modifier sentence reads "46 or earlier". A summary in the state `unsupported` that has both an added and a removed version reads "Supported from Chrome 40, then removed in Chrome 50", with "or earlier" after an approximate version and the target's preview name for a removal in BCD's literal "preview" (Chrome Canary). Without both versions it reads "No support in Chrome". The name agrees with the compact text "40 – 50", so a screen reader user does not hear that the feature was never supported. |
| When does a cell get a disclosure?    | When its history says more than its name: more than one statement, a removal or last-supported version, a flag, a note, a prefix or alternative name the name left out, or a statement whose approximation differs from the summary's (as in a contract 1.0.0 payload). Cells such as "Supported since Chrome 1" get none. |
| Which label does the disclosure get?  | "Flag details" when the only addition is a flag, "Notes" when it is only a note, "History and notes" when there are notes and history, and "History" otherwise.                                                                     |
| What does the history list?           | Every statement of every branch, in the payload's order. Each statement gives one sentence, then its last-supported version, its flags, and its notes. Notes are tokenized by `parseNote` and carried as segments. Only a canonical statement that is neither preview nor removed says "behind a flag" in its sentence; for any other flagged statement, the flag lines that follow carry it. BCD 8.1.9 has two such statements, both with an alternative name. |
| How is a nested row's parent named?   | By its key relative to the top-level row's parent, taken from a stack indexed by depth: `async_iterable` reads "(part of Array.from)".                                                                                           |
| What does the model reject?           | With a `TablePayloadError`, anything that is not an object with a `contract` that is a full `1.minor.patch` version (`1.`, `1.x`, `1.0`, and `1.0.0-rc.1` fail), a `query`, a `browsers` object, and at least one feature. It also rejects a displayed support target whose `browsers` entry has no non-empty `name` or has a `previewName` that is neither absent, null, nor a non-empty string (`invalid-browser`; an entry for a target the table does not display is never read, so it is not checked), a feature with an empty `key` or `name`, a feature whose `name` is not the last dot-separated segment of its `key` (`invalid-feature`), a row more than one level deeper than the row before it, and a feature whose `key` an earlier feature already has (also `invalid-feature`, added by #198 because the renderer keys each row by its feature key; one set lookup for each feature). A `name` that does not end the `key` is rejected, not guessed around, because the model cuts `name` off the end of `key` to name a nested row's parent, and the contract always derives `name` as that last segment, so a mismatch means a malformed payload and a guess would print a wrong "part of" text with no sign of the fault; this is the same stance as the depth rule. Deeper fields are not checked one by one: an error a malformed field causes is rethrown as a `TablePayloadError` with the reason `invalid-content`. The element reports both as `invalid-payload`. |

The model's cost is O(F × T + S + C) in time and space, for F features, T displayed targets, S statements in the displayed cells, and C characters in their notes. A test checks it without trusting the model: it wraps the payload in Proxies that count every property read, then checks that the reads grow linearly when F, T, or S doubles (with a separate support object for each cell and a deep chain of nested rows), and that the reads for one statement, one cell, and one feature stay under fixed ceilings, so a hidden second scan fails. Document 7's string inventory lists the messages the model added and the BCD counts that chose them.

Color is never the sole carrier of meaning: each support state needs a distinguishable non-color affordance (shape, glyph, or text), and the default palette must meet WCAG 1.4.11 (non-text contrast) for icons and 1.4.3 for text. Both are asserted in automated tests. Two systems built specifically for this problem, worth designing from rather than inventing ad hoc: [ColorADD](https://www.coloradd.net/en/) and [ColorSym](https://colorsym.com/), both pairing color with shape for colorblind users. Directly relevant to the default support-state palette and its paired iconography (§4's token surface). #200's test (`packages/element/tests/styles/contrast.test.ts`) computes the ratios from the tokens against each engine's default Canvas colour, white in light and `#121212`, `#1c1b22`, or `#1e1e1e` in dark. The state colours reach at least 4.87:1, above the 3:1 an icon needs, and the borders at least 3.14:1. The stylesheet colours no text, so 1.4.3 stays with the page.

### Disclosure pattern for version history

Expanding a cell to reveal its full timeline uses native `<details>`/`<summary>` rather than a hand-built disclosure. This removes most of the custom-ARIA burden a hand-rolled version would carry: `<summary>` is natively focusable and keyboard-operable (Enter and Space toggle it with no added script), and the browser exposes and maintains open/closed state to assistive technology without a manually managed `aria-expanded`. Notably, focus is never moved by the browser on toggle, so the custom focus-management logic a hand-built version would need — returning focus to the trigger on collapse — simply isn't a problem here.

What still needs deliberate authoring: the `<summary>` content must be an accessible name identifying *which* cell is expanding, not a generic "show more" repeated identically across every cell, and hover must never be the sole means of conveying information, as with any interactive element.

Notes/footnotes are revealed inline within the disclosure, associated with their cell, rather than referenced via a separate superscript marker — a pattern that otherwise strands screen reader users. The element wraps each note in a `<bdi>` element (#198), which isolates the note's text direction, so a note that contains bidirectional control characters cannot reorder the words around it. The Phase 1 pages have no `<bdi>`; it has no role and no attributes, so it should not change what a screen reader says, but only a pass on the built component can confirm that. The CI walks have loaded the built component since #199, so their first transcripts are the first to hear it, and the owner's pass (#212) still confirms it by ear. #198 also added the notes asterisk to the `removed_partial` cell of `phase1-markup/index.html`, inside the hidden glyph span, so the page agrees with the element, which marks every cell whose summary has notes (Document 7, "What is here"). The owner accepted the `<bdi>` and the asterisk on 20 November 2026.

### Responsive behavior

A semantic `<table>` reflowing correctly at narrow widths without losing its semantics is an unresolved problem generally. Default approach: a horizontally scrolling region with `tabindex="0"` (keyboard focusability; a non-focusable scroll region is a WCAG 2.1.1 failure), a `role="region"` accessible name, and a visible focus indicator.

Browser behavior here has been shifting, worth being precise about: Firefox has made scroll containers focusable by default for a long time, and Chrome added the same from 130/132 onward — but only when the scroller has no focusable children. That condition doesn't hold for this table specifically: the version-history disclosures (§5, above) use native `<summary>`, which is itself focusable, so Chrome's auto-focusable-scroller feature does not apply here — Tab would land on the first `<summary>` inside the scroller, not on the scroller itself. Support also isn't universal regardless: MDN's current guidance (`overflow`'s [Accessibility section](https://developer.mozilla.org/en-US/docs/Web/CSS/overflow#accessibility)) still recommends explicit `tabindex="0"` to guarantee keyboard access "in some browsers" that don't do this automatically. So the explicit `tabindex="0"` above isn't legacy caution — for this component specifically it's necessary, not just a safe default, and it costs nothing in browsers that would have handled it natively anyway.

Preferred refinement: container queries, since the reflow decision depends on the component's container rather than the viewport. Shared First discipline applies to container queries as it does to media queries — shared styles outside the query block, each size range self-contained. This lives in `container-queries.css`, one of the files imported into the `bcd-embed.base` layer above — the layer wrapper is declared once at import time (§3), not repeated per file:

```css
/* container-queries.css — no @layer wrapper needed; layer(bcd-embed.base)
   at the import site (§3) already assigns everything in this file */

/* shared — true at every container size */
.bcd-table { inline-size: 100%; border-collapse: collapse; }

@container (width < 40em) {
  /* narrow container: sticky feature column, horizontal scroll */
}

@container (width >= 40em) {
  /* wide container: full grid */
}
```

A sticky first column keeps the feature name visible while support-target columns scroll. `position: sticky` interacting with `border-collapse` inside a scroll container has known quirks, and this needs verification, not assumption, against the component's actual markup.

**What #201 built and found (21 November 2026).** The feature header and the row headers are `position: sticky` with `inset-inline-start: 0` and a background of `var(--bcd-color-sticky-background, Canvas)` at every width, on screen only (`@media not print`). The region's `overflow` sits in `@media not print` too, so a printed table is in the flow and not clipped. The `<table>`, its rows, and its cells keep their table display values at every width, which a test checks at six widths in three engines. The stylesheet has no container query, which departs from the refinement above and from #201's scope, for the reason in the first item below.

- **Container queries cost Chromium five times the layout time at real size.** #201 first built the sketch above: `.bcd-scroller` as a named query container with `container-type: inline-size`, and the sticky column only below 40em. At real size, the cost in Chromium 159 is 51 ms becoming 249 ms at 314 rows, the largest real table: a fivefold increase. The cost grows with the square of the row count, so it was 2.7 s at 1,000 rows, and the synthetic 2,000-row table of the browser tests took 9.2 to 11.9 seconds until two frames after `bcd-load`, against about 0.6 seconds without it, in a wide container and a narrow one alike. The 9 to 14 second figures, from that test and from a bare page (13.6 and 14.1 s), are for that synthetic table, not a real one. Firefox and WebKit did not change. Containment also had a second cost: when the element was a flex item that did not grow and had no width, the region measured 0 pixels wide in all three engines, so the table could not be seen.

  Bisecting the stylesheet showed that the `container` declaration alone causes the slowdown, with no `@container` rule at all and wherever the container sits; an independent review found it even on an ancestor outside the table. On a bare page with rows of four `<details>` cells, `contain: style` reproduced it and `contain: inline-size` did not, so the trigger is the style containment that a query container applies. Setting `summary { display: block }` removed the cost, and a `counter-reset: list-item` on each `<details>` or cell did not, so it comes from the `<summary>` elements, which are `display: list-item`, inside one style containment scope. Changing how `<summary>` is displayed could change what screen readers say, and a media query would track the viewport, not the container, so the column is sticky at every width instead. That is harmless where the table fits, because a sticky cell only moves when its scroll container scrolls. `tests/styles/containment.test.ts` and a browser test fail if the stylesheet applies style containment again. Revisit when a Chromium release lays out the bare page in linear time.

- **Long feature names.** A long identifier at depth 5 could make the sticky column nearly as wide as a 320 CSS pixel region, so the other columns could never scroll out from behind it. The row headers now have `box-sizing: border-box` and `min-inline-size: 10em`, and their `<code>` has `overflow-wrap: anywhere`, so in a region too narrow for the table the column shrinks to 10em, indent included, and the name wraps inside it. Where the table fits, the column keeps the name's full width. No `display` changed and the hidden sentence span did not move. A test at 320 CSS pixels, with a name of 63 characters at depth 5, scrolls each of the six columns beside the sticky column and checks that it is fully in view and uncovered, in three engines.
- **The element's height.** The grid of #200 that hides a bare text fallback had `grid-auto-rows: 0` and no explicit row, so the row that holds the table was implicit too, and a loaded element and its render container were 0 pixels tall in all three engines: the page's next content was drawn over the table. #201 found it with the visual fixture, which places two tables in a row, and adds `grid-template-rows: auto`, so the first row fits the table and only the fallback text's rows are 0. A test checks that content after the element starts below the table.
- **Right to left and forced colours.** In `dir="rtl"`, the sticky column sticks to the right of the region, a support cell draws its inline-end border on the left, and all four borders of the scrolled sticky cell stay painted, in three engines. Under Playwright 1.65.1's forced-colours emulation, Chromium 159 and Firefox 159 replaced author colours, while WebKit 27.2 matched `(forced-colors: active)` but kept them, which differs from #200's note that only Firefox forced colours. Where colours are forced, the sticky cells are painted in `Canvas` and their borders stay visible while the table scrolls.
- **Borders.** `@mdn/browser-compat-data` 8.1.9 notes for Firefox that borders do not display on sticky table headers under `border-collapse: collapse` ([bug 1727594](https://bugzil.la/1727594)). A test that reads the painted pixels around a scrolled sticky row header found the problem in all three engines, not only in Firefox: with collapsed borders, the inline-start border was missing in Chromium 159, Firefox 159, and WebKit 27.2, and the inline-end border was missing or faint in all three, while the block borders stayed. So the table uses `border-collapse: separate` with `border-spacing: 0`. Each cell draws its block-end and inline-end border, the first header row adds the block-start side, and the feature column adds the inline-start side, so every line belongs to one cell and moves with it. With that model, all four sides of the scrolled sticky cell matched the border colour exactly in all three engines.
- **The sticky background.** Positioned cells paint above the cells that scroll beneath them, so they need a background, and the stylesheet sets none elsewhere. `Canvas` follows the inherited `color-scheme`. A registered `<color>` token with a `Canvas` initial value resolved to white under `color-scheme: dark` in all three engines, so the token is unregistered and read with a fallback. A page with its own background sets the token to match.
- **Keyboard.** The region takes Tab, and the arrow keys scroll it in all three engines. WebKit animates keyboard scrolling and stops when the key comes up, so the test holds the key for 200 ms; a press with no delay often moved nothing.
- **Screen readers.** The CI walks use Playwright's "Desktop Firefox" and "Desktop Safari" devices, 1280 CSS pixels wide, where the fixture table fits, so they hear the sticky cells and the separate border model, but not a table that is scrolled. A scrolled walk is left to the owner's pass (#212).

Worth tracking, not relying on yet: a genuine fix for the classic sticky-header-plus-sticky-first-column problem — this table's exact requirement — is in progress in the CSS Working Group, letting `position: sticky` track a different scroll container per axis (first column against the table wrapper, header against the document) instead of one shared scroller for both. Per [Bramus Van Damme](https://www.bram.us/2026/03/30/css-sticky-per-axis/), it requires `overflow: auto clip` on the wrapper rather than plain `overflow-x: auto`, which implicitly enables vertical scrolling too and re-traps the header. As of this writing it's Chrome-only and experimental (landed behind a flag in Chrome 148, `@supports` detection following in Chrome 150, stable shipping still pending); Firefox and Safari don't implement it. Not something v1 can depend on — the single scroll region with a sticky column, as #201 built it, remains the cross-browser default — but worth revisiting at Phase 3 (§10), since it would let the design drop the duplicated-header workaround once support broadens.

Alternative considered and rejected: a card-per-support-target layout at very narrow widths, which abandons the `<table>` element and its semantics.

### Motion and preference

Expansion animation respects `prefers-reduced-motion`. Default palette respects `prefers-color-scheme`; `light-dark()` follows an author-set `color-scheme` where present.

## 6. Performance

Multiple tables per page is the expected case.

The component does not fetch until needed, by default: an `IntersectionObserver` defers both the payload request and the rendering until the section nears the viewport. It does not defer loading the rendering code, because the renderer is a static import (below). This is the `loading="lazy"` default (§4); `loading="eager"` skips the observer and fetches immediately, for the specific cases where deferral costs more than it saves (§4).

Requests are deduplicated and cached at module level, so multiple tables querying overlapping keys on one page produce one fetch, not several.

Rendering happens once from fully resolved data rather than progressively, avoiding layout thrash. Payloads are compressed at the service (Document 1 §9); this is load-bearing for the performance budget.

The package ships as ESM and tree-shakeable. `sideEffects` in `package.json` is deliberately **not** a blanket `false`: the element package's entry point calls `customElements.define(...)` at module scope — a genuine side effect a bundler must not remove, and exactly what a bare `"sideEffects": false` risks dropping ([rollup/rollup#5538](https://github.com/rollup/rollup/issues/5538) documents this happening for prototype-mutation side effects; the underlying `sideEffects`/`moduleSideEffects` confusion is tracked in [rollup/rollup#5987](https://github.com/rollup/rollup/issues/5987)). [vitejs/vite#14321](https://github.com/vitejs/vite/issues/14321) covers the equivalent gap for CSS imported via JS, relevant if base styles are ever distributed that way rather than as a plain `.css` file. Correct configuration: the array form, listing the file that calls `customElements.define` and the stylesheets, which the scaffold issue sets as `"sideEffects": ["./dist/index.js", "./dist/*.css"]` (#194), leaving `core`, `schema`, and the pure rendering helpers genuinely tree-shakeable. #206 verified it with a consumer build rather than assuming it: a throwaway Vite project that imports the built package defines `bcd-compat-table` when the built page runs, and the same build with `sideEffects` set to `false` leaves the element undefined (`packages/element/tests/consumer-build.test.ts`). A bundle analysis of the entry showed no `zod` or schema code in it (Document 10, #206 section).

**The renderer boundary: one static import unless the renderer is large.** An earlier draft put the table renderer in a separate chunk from the element shell. The decision now is that the renderer stays a static import, so the package's entry is one file, unless the packaging check (#206) measures the renderer alone at more than 8 KB compressed with gzip, the same measure as the budget below (#206 says only "compressed", so this document fixes it as gzip to make the two numbers comparable); only then does #206 propose a lazy chunk as a follow-up issue. The reason to prefer one file: the tooling spike found that Vite 8.3.8's library mode emits a second, content-hashed chunk for every dynamic `import()`, and the entry refers to it by that hashed name, so a consumer who copies only the entry file loses the lazy code ([Document 10, #188 section 5](10-component-spikes.md#5-vite-library-mode-and-dynamic-import)). **Decision recorded by #206 (21 November 2026): the renderer stays a static import.** `size-limit` 14.3.0 with `"gzip": true` measured the renderer alone, that is `src/render/table.ts` with the two modules it imports, `render/status.ts` and the message formatter, and `"ignore": ["lit"]`, at 1.74 kB (1,736 B), against the 8 kB threshold. The initial import measured 16.68 kB (16,676 B) with Lit and `@lit/task`, against the 25 kB budget below. The renderer's measure excludes Lit on purpose: bundled with Lit the same file counts 8.10 kB (8,098 B), but the shell's `LitElement` base class already brings in `lit-html`, the template engine that the renderer's templates run on, so a lazy chunk could move only the renderer's own 1.74 kB. The 8.10 kB figure sits just over 8,000 B, but under 8,192 B (8 KiB), so if the rule's "KB" means 1,024 bytes, the renderer with Lit counted is under the threshold too. `size-limit` reads `kB` as 1,000 bytes, and the 1,736 B reading does not depend on the choice. The owner can overrule this reading; under it the follow-up issue would save about 1.7 kB of the 16.68 kB. Both measures are checked on every `pnpm build` by entries in `packages/element/.size-limit.json`, so a renderer that grows past 8 kB fails the build. A `size-limit` entry can only fail; it cannot open an issue. Failing is the right behaviour because the rule is a decision point, not a defect: the person who sees the failure either proposes the lazy chunk as the follow-up issue this section describes, or records why the static import stays and raises the limit in the same commit. Silence would let the renderer outgrow the rule unnoticed. No follow-up issue is proposed now. The same chunking applies to the locale tables that §4 loads on demand by dynamic import: each would ship as its own hashed file. v1 ships English only, so no locale chunk exists yet.

**Budget, in numbers.** General guidance for optimal web performance puts an initial JavaScript bundle under 250 KB uncompressed, 50–100 KB compressed — but that is a budget for a whole page, and this component is a guest on someone else's. Its own target: **25 KB compressed with gzip, or less**, for the initial import (element shell, Lit, and the renderer together), excluding payload data, asserted by a `size-limit` check in continuous integration (CI) that fails the build when exceeded (#206), rather than observed informally. What the tooling spike measured about that check ([#188 section 4](10-component-spikes.md#4-size-limit)):

- `size-limit` 14.3.0 with `@size-limit/preset-small-lib` exits 1 over the limit and 0 under it, so it can fail CI.
- It counts an imported `lit` in the total unless the entry sets `ignore: ["lit"]`. A probe Lit element measured 5,341 B with Lit counted and 184 B without. This budget includes Lit, so the entry must not ignore it.
- By default it adds every chunk the entry produces, including a dynamically imported one; `entry: ["main"]` limits the total to the main chunk and its static imports.
- The preset measures with Brotli, not gzip. Every spike number above is Brotli. The budget is measured with gzip, so the `size-limit` entry sets `"gzip": true`. The review of this amendment read that option in `size-limit` 14.3.0's `index.d.ts` (`gzip?: boolean`, "With true it will use Gzip compression and disable Brotli compression"); the spike did not run it, so #206 confirmed it against the installed copy: with `"gzip": true`, `size-limit` 14.3.0 measured `dist/index.js` at 16,676 B, and without it at 15,100 B with Brotli. The CI check is `size-limit` inside `pnpm --filter @bcd-embed/element build`, which `pnpm check` and the CI `check` job run. `size-limit` reads `kB` as 1,000 bytes, so the limit is 25,000 B. A 30 kB incompressible constant added to the entry raised the size to 40.07 kB and the command exited with code 1; removing it brought the size back to 16.68 kB and the exit code to 0 (Document 10, #206 section).

These limits are client-side limits specifically: server-side code (`generator`, `server`, Zod validation) carries no comparable ceiling, which is exactly why Zod stays out of the element bundle (§2, Document 2 §2) while remaining the right tool on the server.

## 7. Data-flow modes

Fetch-from-API and works-without-JavaScript are not simultaneously achievable without a build-time path, so this needs resolving explicitly rather than being discovered later.

**v1 priority is fetch mode, then data mode.** Full server-side rendering of the markup is deferred (see below) — it is a reasonable thing to want eventually, but committing to it now, before fetch mode has shipped and been used, is scope creep this document should not lock in.

**Fetch mode (default).** Set `query`; the component fetches and renders. The no-JavaScript fallback is content the author writes as the element's children; the component supplies no default fallback and invents no link. The children show before the element upgrades, while it loads, and after an error, and are hidden once the table renders (§4, "Fallback content"). For example, an author who wants readers without JavaScript sent to MDN Web Docs (MDN) writes the link:

```html
<bcd-compat-table query="css.properties.display">
  <p>
    <a href="https://developer.mozilla.org/en-US/docs/Web/CSS/display#browser_compatibility"
      >Browser compatibility for <code>display</code> on MDN Web Docs</a
    >
  </p>
</bcd-compat-table>
```

Prefer an element, such as the `<p>` above, to bare text. The base stylesheet hides both once the table loads, without leaving space for either (#200), but under React a single string child that changes destroys the render container until the element restores it (§4, "Fallback content").

**Data mode has two variants, both no-fetch, differing in how the payload arrives.**

The first is the `.data` property: set directly with a contract-conformant payload obtained at build time via `@bcd-embed/core` (Document 2 §7). This requires a script to run and assign the property, so it depends on a build step or a small hydration script executing before the element does anything useful.

The second, worth building because it removes that dependency, is an inline JSON island — a sibling `<script type="application/json">` carrying the payload, referenced by the element rather than assigned to it:

```html
<script type="application/json" id="bcd-data-css-properties-display">
  { "contract": "1.1.0", "query": "css.properties.display", ... }
</script>
<bcd-compat-table query="css.properties.display" source="bcd-data-css-properties-display"></bcd-compat-table>
```

`source` takes the `id` of a JSON script element; the component reads and parses it in `connectedCallback`, synchronously when the script is there — no fetch, no property assignment from any script. **Which order works (#205).** The Lit spike found that when the element is defined before the parser reaches it, `connectedCallback()` runs before the parser has read anything after the element's start tag ([Document 10, #187 section 1](10-component-spikes.md#where-the-container-lands-depends-on-when-the-element-is-defined)). #205 tested `source` against that and confirmed it: in Chromium, Firefox, and WebKit a script written after such an element does not exist at `connectedCallback` time ([Document 10, #205](10-component-spikes.md#issue-205--the-source-mode-and-the-order-of-the-script)). So the element handles it. When the `id` matches nothing and `document.readyState` is `"loading"`, the parser may still reach the script, so the element waits and reads on the document's `readystatechange`, which fires when parsing ends. The wait shows nothing and fires no event. Once parsing has ended, an `id` that matches nothing is `source-missing`. The consequence for authors: a script before the element, in the same tree and with no earlier element that has the same `id`, always works, and a script after it works while the page is being parsed, whether the element is defined first or last. A script that inserts both fragments into a page that has finished loading must insert the JSON script first, because nothing is left to wait for. The element looks the `id` up in its own tree, the shadow root that holds it or else the document, so a script in a different shadow root is not found. The element accepts one kind of target: an HTML `<script>` whose `type` is `application/json` in any letter case, with no parameters. It never reads the text of another element, and `getElementById` returns the first match in tree order, so a non-script element that shares the `id` and comes earlier makes the result `source-missing`, at once, even while the page is being parsed, because a script with the same `id` further down can never be the first match. The reader calls `JSON.parse` on `textContent` and evaluates nothing. Any exception from it, including the `RangeError` an engine may throw for extreme nesting, is `source-invalid-json`, because an exception that escaped would abort `connectedCallback`. The scope check does not use `instanceof ShadowRoot`, which is false for a shadow root made by another window; it looks for `getElementById`. Parsing costs O(n) time and space for n characters of script text, and the lookup is expected O(1); the element parses once per id, so updates cost nothing extra. Changing the `source` attribute to another `id` reads that script, and fires one event, as any new input does. **Refreshing:** the element never watches the script, so a page that changes the JSON gives the new payload a new script and `id`, or removes `source`, lets the element update, and sets it again; removing and setting it in the same task does nothing, because the one update sees the same `id` (#205). The page's generator must also replace every `<` in the JSON with the six-character escape `\u003c` (a backslash, `u`, `0`, `0`, `3`, `c`) (#205). Escaping only the closing script tag is not enough. The tokenizer ends the script before the element sees any text, and two sequences matter: a closing script tag, which ends the script at the note so the JSON is cut and the result is `source-invalid-json`, and `<!--<script>`, which moves the tokenizer into the script data double escaped state (HTML Standard, 13.2.5, "Script data double escaped state"; see also 4.12.1.3, "Restrictions for contents of `script` elements"), where the next `</script>` no longer ends the script, so the rest of the page, the element included, is swallowed. A browser test shows both failures and the escaped success. Escaping every `<` removes both, and the element cannot check it. A static-site generator only has to emit two plain HTML fragments — the script tag and the element referencing it — a lower bar than requiring a hydration script to run and set a property in the right order. `id` naming is the author's responsibility; a documented convention (`bcd-data-{query-with-dots-as-dashes}`) avoids collisions across multiple tables per page without the component enforcing anything. Both `.data` and `source` are no-fetch, no-loading-state paths; `source` is the one requiring no script execution at all beyond the component's own.

**Server-side rendering of the markup — deferred, not v1.** Rendering the actual table HTML on the server (rather than just the data) would extend data mode's no-JavaScript story to cover markup as well, and Lit's SSR support makes it technically tractable. But it adds a real implementation and testing surface (Document 3 §9, §10) for a capability neither fetch mode nor the inline-JSON variant of data mode requires, and nothing in the project's stated goals (Document 0 §3) commits to it. It is left as a candidate future addition once the two v1 modes have shipped and are in use, rather than designed and built now on spec.

Fetch mode and both data-mode variants are one component with configurable data-flow, not three components, keeping the contract and documentation single.

## 8. Framework interoperability

**React 19 decides by the element instance, not by the value's type.** In client rendering, React 19 assigns a prop as a property when the custom element instance has a property of that name, and as an attribute otherwise ([React 19 release post, "Support for Custom Elements"](https://react.dev/blog/2024/12/05/react-19)). The Lit spike confirmed this in React 19.3.1: React checks `key in domElement` at the moment it applies the prop, and the value's type matters only afterwards, on the attribute path ([Document 10, #187 section 5](10-component-spikes.md#5-react-19-setting-data-on-the-element)).

**What this means for `data`.** React finds the `data` property only when Lit's accessor already exists, which is when the element has been defined before React renders it. In the Lit spike's words: "If the element is not defined before React renders it, `data` becomes the attribute `"[object Object]"` and the payload is lost" ([#187, finding 1](10-component-spikes.md#findings-for-the-document-3-amendment-192)). The spike recorded each load order:

| When the element is defined           | What React 19.3.1 does with `data`                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| Before React renders it               | Sets the property; `el.data` is the same object                                        |
| After React renders it                | Sets the attribute `data="[object Object]"`; after the upgrade `el.data` is `null` (the spike's stand-in element left it `undefined`; ours sets `null` in its constructor), so the payload is lost |
| After, then React renders a new value | Sets the property, because the accessor now exists                                     |
| After, with a `ref` callback          | The callback sets the property; Lit keeps it through the upgrade                       |

The payload is lost in the second row because `data` is declared with `attribute: false`, so Lit never reads the attribute. So the element's module must run before React renders the element, for example by importing `@bcd-embed/element` at the top of the module that renders it. Where the load order cannot be guaranteed, the recommended form is a `ref` callback that assigns `data`, which works in every load order. One caveat applies: React runs a `ref` callback again only when it is a different function from the previous render, so an inline callback runs on every render, while a memoised one runs once and later changes to `data` need another path, such as the `data` prop once the element is defined ([#187 section 5](10-component-spikes.md#5-react-19-setting-data-on-the-element)). The spike did not test a primitive prop or repeated `ref` assignment. React 19 attaches the event listeners through the props `onbcd-load` and `onbcd-error`, and #207 confirmed it, alongside Vue 3.5.45 (`@bcd-load`, with `:data.prop` for a property that works in every load order) and Svelte 5.57.3 (`onbcd-load`, and a plain `data` binding that sets a property before the upgrade). The results, including a WebKit bug that affects Svelte when the element is defined late, are in [Document 10, #207](10-component-spikes.md#issue-207--framework-fixture-pages-react-vue-and-svelte).

**Server rendering is different.** The same release post says that in server-side rendering React renders primitive props as attributes and omits objects, so `data` never reaches server-rendered HTML. The spike tested client rendering only. A server-rendered page passes the payload through `source` (§7) or assigns `data` on the client.

**String children.** React treats a single string child of a custom element as text content, and when that string changes it assigns `textContent`, which replaces every child, including the render container ([#187 section 3](10-component-spikes.md#a-single-string-child)). The element restores the container (§4, "Fallback content"), but under React the fallback is better written as an element than as a bare string.

Older React versions do not handle custom element properties consistently; the documentation states the React 19 rule above and does not promise more for older versions.

A thin React wrapper is a plausible future addition, not a `v1` deliverable.

## 10. Implementation plan

**Phase 1 — semantic structure, statically.** Hand-write target table markup for a set of fixtures chosen for complexity, not familiarity, with no component code. Establish header association, cell naming, and disclosure structure; validate against a screen reader before any Lit code is written. This ordering is deliberate: the accessible structure is the load-bearing constraint and should not be retrofitted around a rendering approach chosen for other reasons. The owner decided on 18 November 2026 that only work holding no table markup could merge before the Phase 1 pass (#186) closed, and then on 19 November 2026 to run every manual screen reader pass at the end. So #186 no longer holds any issue, the element's template (#198) included. #198 builds the Phase 1 markup with variant A, by Document 7's rule that "Variant A is the simpler markup, so it wins unless a screen reader announces variant B more completely"; the pass at the end can still reverse that. The CI walks have so far shown no advantage for variant B (Document 7, "First automated results"). The fallback rule in §4 is decided, so nothing in it holds #198 either.

**Phase 2 — element in data mode.** Lit element taking `.data`, producing the Phase 1 markup, with the fallback rules and the `bcd-load` and `bcd-error` events (§4). No fetching. Fully testable against fixtures; completable before the service exists. #198 built it. A browser test compares the element's table with `phase1-markup/index.html` element for element and attribute for attribute, and `packages/element/README.md` records the bound on the size of the rendered tree and the render time of a 2,000-feature table.

**Phase 3 — styling.** Base styles in the cascade layer, registered custom properties, container queries under Shared First, `light-dark()` for dark mode, print styles. Verify that un-layered author CSS overrides every base style, since this is the core assumption behind the light-DOM decision.

**Phase 4 — fetch mode.** Async task, loading/error states, request cache and deduplication, `IntersectionObserver` deferral and the `loading` attribute that controls it, `endpoint` override. Integrate against the live service. A request that fails without a readable response is a temporary failure, not a bug in the page: the hosted service's rate limit answers with a Cloudflare 429 that has no CORS header, so the browser reports it as a network error (Document 1 §8, Document 9). The element shows its fallback content, fires `bcd-error` with `reason: "network"` and `status: null` (§4), and does not retry on its own. #203 built this phase. The element runs a `Task` from `@lit/task` with `autoRun: false` and starts it from `willUpdate`, because the element decides when a request may start: only while `.data` is `null`, only once the lazy wait is over, and never while the element is out of the document. A new `query` or `endpoint` while a request is pending aborts the old run, and `Task` drops the old result, so the old answer neither renders nor fires an event. Removing the element aborts its wait, so no event fires for an answer that arrives later, and the viewport observer is disconnected; adding it back asks again, and the request cache answers without a second request. The one test against the live service is `pnpm --filter @bcd-embed/element test:live`, which is not part of `pnpm check`. The size budget rose from 7 kB to 8.5 kB with Brotli, without Lit, because the feature client and the request cache entered the bundle; the package measured 8.26 kB.

**Phase 5 — interaction.** Disclosure, focus management, keyboard paths, reduced motion.

**Phase 6 — the `source` inline-JSON variant of data mode.** Reading and parsing the referenced `<script type="application/json">` in `connectedCallback` (§7), with the same rendering path as the `.data` property. No SSR, no hydration — this is still client-side parsing of an already-present payload, not markup rendered on the server.

**Phase 7 — documentation, demo site, and packaging verification.** Including a bundle-analyzer pass confirming the `sideEffects` configuration (§6) actually tree-shakes as intended and does not drop the custom element registration.

**Deferred, not scheduled as a v1 phase: full server-side rendering of the markup** (§7). Revisit once fetch mode and both data-mode variants have shipped and are in real use — building it now, ahead of that, is the scope creep the project should avoid locking in.

## 11. Design decisions settled during review

**Default support-target set — resolved: Chrome, Firefox, Safari, Node.js.** The API returns every browser and runtime BCD tracks, including Deno, Bun, Edge, Opera, and mobile variants; showing all of them by default would be noisy. Chrome, Firefox, and Safari are included because they map to the three independent rendering engines (Blink, Gecko, WebKit) — the actual signal a reader needs for "does this work everywhere" — not a popularity pick. Chromium-based browsers like Edge and Opera track Chrome's Blink closely enough that including them by default would mostly repeat the same answer.

Node.js is included alongside them, not treated as an opt-in extra: a large share of what this table renders is JavaScript API compatibility (`javascript.builtins.*`, `api.*`), and "does this run in Node" is a first-class question for that data, not a specialist one. Deno and Bun stay out of the default — a real but smaller audience — added via `browsers` (§4) without imposing the extra column on everyone else.

The default set is additionally filtered by the payload: a defaulted target with no entry anywhere in the response's support data is dropped rather than rendered as a permanently empty column, so Node.js appears exactly where BCD has something to say about it — JavaScript and API data, not `css.*`. An explicitly set `browsers` attribute is exempt from this filtering and renders exactly what it lists, including a "no data" column if the author asks for one (§4).

**"Flag means unsupported" convention — resolved: no.** Document 1 §6 leaves `behindFlag` orthogonal to `state` and defers the display decision to the consumer; the component now makes that call. Flag-gated support displays as its own distinct state rather than collapsing into unsupported, since collapsing it discards information a reader may specifically want (a technical writer covering an experimental feature, for instance, needs to know it exists behind a flag, not just that it's a flat "no"). A consumer wanting MDN's stricter convention can still compute `state === "supported" && !behindFlag` themselves (Document 1 §6); the component's own default does not make that choice for them.

**Element name — resolved: `<bcd-compat-table>`.** Not bikeshedded further; it is clear, matches the `bcd-embed` project naming, and is worth shipping over continuing to deliberate a permanent-but-not-consequential choice.
